“Webhook signature verification failed”

Stripe, GitHub, Shopify and Slack all reject signatures for the same four reasons. The provider names differ, the fix rarely does — and in almost every case the secret is fine and the body is the problem.

What each provider actually signs

This table is the whole article. Nearly every failure is a mismatch between one of these columns and what your code does.

ProviderHeaderSigned stringEncodingReplay window
StripeStripe-Signature <t>.<body>hex, after v1=5 min
GitHubX-Hub-Signature-256 the raw bodyhex, after sha256=none
ShopifyX-Shopify-Hmac-Sha256 the raw bodybase64, no prefixnone
SlackX-Slack-Signature v0:<t>:<body>hex, after v0=5 min

All four are HMAC-SHA256. That similarity is the trap: code copied from a Stripe tutorial looks right against a Shopify webhook and will never match.

Cause 1 — you signed a re-serialised body

By far the most common. Your framework parsed the JSON, and you passed the parsed object (or a re-stringified version of it) to the verifier. Key order and whitespace changed, so the bytes differ, so the HMAC differs.

// wrong — req.body has already been parsed and re-serialised
verify(JSON.stringify(req.body), signature, secret);
// Next.js route handler
const raw = await request.text();

// Express
app.post("/webhook", express.raw({ type: "application/json" }), handler);

// NestJS — rawBody is undefined unless you ask for it
NestFactory.create(AppModule, { rawBody: true });

A quick diagnostic: log body.length at the very top of your handler and compare it with the Content-Length header. If they differ, something between the socket and your code has rewritten the payload.

Cause 2 — the wrong secret, or the right secret from the wrong place

  • Stripe: the signing secret is per endpoint and starts with whsec_. The one printed by stripe listen is not the one your deployed endpoint uses — mixing them up is the classic. An sk_ API key will never verify.
  • Shopify: it's the app's API secret key, not the access token.
  • Slack: the signing secret, not the bot token, not the verification token.
  • GitHub: whatever string you typed into the webhook's secret box — with no trailing newline, which is easy to acquire if you piped it from a file.

Cause 3 — the wrong encoding

Shopify's signature is base64. Everyone else's is hex. Comparing a base64 digest with a hex one fails every time and looks exactly like a wrong secret.

// Shopify
crypto.createHmac("sha256", secret).update(raw).digest("base64");
// Stripe / GitHub / Slack
crypto.createHmac("sha256", secret).update(signedString).digest("hex");

When you do compare, use a timing-safe comparison of equal-length buffers — crypto.timingSafeEqual throws if the lengths differ, so check length first.

Cause 4 — a valid signature that's simply too old

Stripe and Slack both sign a timestamp and enforce a five-minute window. A replayed request — a captured payload, a fixture in an old test — can have a perfectly correct HMAC and still be rejected. If your signature matches but verification fails anyway, check the age before you change anything else.

Once it verifies, you're not finished

A verified signature only proves the request is genuine. It says nothing about what your handler then does with it — and the expensive bugs live there: granting a purchase twice because the provider redelivered, or leaving a download accessible after a refund.
