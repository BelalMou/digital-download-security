Payments engineering

Four ways a digital-download store leaks money

Selling files is the “easy” e-commerce case: no stock, no shipping, no returns logistics. That reputation is exactly why the security gets skipped — and the same four holes turn up in tutorial after tutorial.

Each leak below comes with a runnable test that fails against the naive implementation and passes against the fixed one.

npm test — 22 tests, ~200 ms, no database or network required. Everything is mocked, so it runs anywhere and there is nothing to configure.

Leak 01

The webhook that grants two purchases

Stripe delivers webhooks at least once. Retries happen on timeouts, on 500s, and sometimes for no reason you will ever discover. The naive handler is:

vulnerable 
const session = event.data.object;
await db.purchase.create({ data: { ... } });   // runs twice on redelivery

Two rows, one payment. Revenue reporting is now wrong, the buyer may get two confirmation emails, and any per-purchase entitlement is doubled.

The fix is not “check if it exists first” on its own — that is a race. It is a unique constraint on the Stripe id, so the database refuses the second write, with the check as the fast path:

fixed 
const existing = await db.findPurchaseBySessionId(session.id);
if (!existing) {
  await db.createPurchase({
    stripePaymentId: session.id,   // unique index catches the race
    ...
  });
}

Tested: the second delivery still returns 200 — so Stripe stops retrying — while createPurchase was called exactly once.

Leak 02

The signature you forgot to verify

Your webhook endpoint is a public URL that grants entitlements. If it does not verify the signature, anyone who guesses it can mint themselves purchases by POSTing a plausible JSON body.

fixed 
const event = stripe.webhooks.constructEvent(
  await request.text(),                       // RAW body
  request.headers.get("stripe-signature"),
  process.env.STRIPE_WEBHOOK_SECRET
);

Two traps live here:

  • The raw body matters. If your framework parsed the JSON and you re-serialise it, key order and whitespace change, the computed signature will not match — and the usual “fix” people reach for is to skip verification entirely. Read the body as text.
  • Fail closed. A verification error is a 400, not a try/catch that shrugs and carries on.

Tested: a missing signature header, a forged payload, and that verification receives the raw bytes — whitespace included — rather than a re-serialised object.

Leak 03

The download URL that gets shared

If a purchased file sits at a guessable or permanent URL, it will end up in a Discord server. Two things have to be true: ownership is checked server-side against the session — not by a query parameter, and not by hiding the link in the UI — and the URL expires.

fixed 
if (!purchase || purchase.buyerId !== userId) {
  return new Response("Not found", { status: 404 });
}
const url = await storage.createSignedUrl(purchase.fileKey, 3600);

Note the 404. Returning 403 for “exists but isn’t yours” and 404 for “doesn’t exist” tells an attacker which purchase ids are real. Return the same thing for both.

Tested: a non-owner gets 404, no signed URL is ever minted for them, and the foreign-purchase response is byte-identical to the missing-purchase response.

Leak 04

The refund that doesn’t revoke anything

This one is nearly universal, because refunding happens in the Stripe dashboard and never touches your app. The customer gets their money back and keeps the file.

fixed 
await db.purchase.updateMany({
  where: { stripePaymentIntentId: intentId, refundedAt: null },
  data:  { refundedAt: new Date() },
});

Three details worth stealing:

  • Refund events reference the PaymentIntent, not the Checkout Session. If you only stored the session id, you cannot map a refund back to a purchase at all. Store both at fulfilment — this is the detail that bites hardest, because it is invisible until the first refund.
  • Partial refunds should not revoke. The buyer still paid for part of it. Compare amount_refunded against amount. Disputes always revoke.
  • Do not delete the purchase row. It is the financial record the refund refers to. Add a refundedAt column and check it at download time.

Tested: a full refund and a dispute both revoke; a partial refund does not; a refunded purchase returns 410 and mints no URL.

Bonus

The price you took from the browser

Better known than the four, but still worth stating plainly: never accept an amount from the client. Read it from your own database when you create the checkout session, and read it from Stripe when you record the sale.

Tested: with hostile amount and price values planted in the session metadata, the recorded amount still comes from Stripe’s amount_total.

What this is, and what it isn’t

This is a reference for the security-critical paths, not a store. The handlers take a standard Request and return a Response, with their dependencies injected — so they drop into Next.js, Remix, Hono or Express unchanged, and the tests need no framework at all. It is deliberately small, because the tests are the point.

It is MIT licensed and complete enough to fix your own store without buying anything.
