Payments engineering

Your Stripe webhook fired twice. That’s not a bug.

Stripe delivers webhook events at least once — duplicates are part of the contract, not a failure. If a second delivery grants a second purchase, the problem is in the handler, and “check if it already exists” on its own won’t fix it.

Why you got two

Any of these produces a redelivery, and all of them are normal:

  • Your endpoint took longer than Stripe’s timeout, so it retried — even though your handler completed successfully.
  • Your handler threw after doing the work, returning a 500. Stripe sees failure and retries something that already happened.
  • A deploy, cold start, or proxy dropped the connection mid-response.
  • Occasionally, no discernible reason at all. At-least-once means what it says.

You cannot make deliveries unique. You can only make fulfilment idempotent.

Why check-then-insert isn’t enough

The obvious fix looks right and fails under exactly the conditions that cause duplicates:

racy 
const existing = await db.purchase.findFirst({
  where: { stripePaymentId: session.id },
});
if (!existing) {
  await db.purchase.create({ data: { ... } });   // two requests can both reach here
}

Two deliveries arriving close together interleave:

A → SELECT … → not found
B → SELECT … → not found
A → INSERT → ok
B → INSERT → ok — two rows, one payment

The window is milliseconds, which is precisely the gap between a retry and the original when a timeout fires. This is why the bug shows up in production and never in testing.

The fix: let the database enforce it

Put a unique constraint on the Stripe id. The check becomes a fast path; the constraint is what actually guarantees correctness.

correct 
// schema
model Purchase {
  stripePaymentId String @unique   // the Checkout Session id
  // …
}

// handler
const existing = await db.purchase.findFirst({
  where: { stripePaymentId: session.id },
});
if (!existing) {
  await db.purchase.create({
    data: { stripePaymentId: session.id, /* … */ },
  });
}

Now the racing second insert violates the constraint and throws. Return a 500, Stripe retries once more, the findFirst now sees the row, and the handler returns 200 cleanly. The outcome is one purchase regardless of how the deliveries interleave.

Use the right id. The Checkout Session id (cs_…) is stable across redeliveries of the same completed checkout. The event id (evt_…) is also fine and is more general — but note two different events can describe the same underlying purchase, so pick the id that identifies the thing you don’t want to do twice, not merely the message.

Three things people get wrong next

Returning 500 because a side effect failed

If your confirmation email throws after the purchase row was written, and you let that propagate, Stripe retries a fulfilment that already succeeded. Let side effects fail quietly:

sendConfirmation(purchase).catch((err) => console.error("[email]", err));

Acking with 200 when nothing was written

The mirror image. If the database was genuinely unreachable, you want the retry — return a 500. Idempotency is what makes that retry safe.

Trusting an amount from metadata

While you’re in here: read the amount from session.amount_total, never from metadata or anything else the client can influence.

Test it, don’t assume it

The assertion worth writing is that a second delivery still returns 200 while the create ran exactly once:

it("does not double-grant when Stripe redelivers", async () => {
  findPurchaseBySessionId.mockResolvedValue(null);
  await handleStripeWebhook(req(), deps);          // first delivery

  findPurchaseBySessionId.mockResolvedValue({ id: "p1" });   // now exists
  const second = await handleStripeWebhook(req(), deps);

  expect(second.status).toBe(200);                 // so Stripe stops retrying
  expect(createPurchase).toHaveBeenCalledTimes(1); // still one grant
});
