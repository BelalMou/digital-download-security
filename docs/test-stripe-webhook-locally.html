Test a Stripe webhook locally without the CLI

The Stripe CLI is good, but it needs a login, it holds a tunnel open, and there are events it cannot easily produce. Sometimes you just want to POST one signed request at localhost and see what your handler does.

What a webhook request actually is

There is nothing magic in it. Three things:

  1. A JSON body — the event.
  2. A Stripe-Signature header: t=<unix-seconds>,v1=<hmac>.
  3. The HMAC, which is SHA-256 over the literal string <t>.<raw body>, keyed with your endpoint's whsec_ signing secret.

If you can produce those, you can test your handler with curl, from a test suite, or from CI — with no Stripe dependency at all.

One-step version The signature tool builds the whole curl command: pick an event, paste your test signing secret, and it prints a ready-to-run request. It computes the HMAC in your browser — nothing is uploaded, which matters because the input is a signing secret.

Doing it by hand

Compact the body to one line first. The signature covers the exact bytes you send, so if you sign a pretty-printed payload and POST a minified one, verification fails — and you will spend an hour blaming the secret.

# bash
SECRET='whsec_your_test_secret'
BODY='{"id":"evt_test","object":"event","type":"checkout.session.completed","data":{"object":{"id":"cs_test_1","amount_total":3900,"currency":"usd","payment_intent":"pi_test_1","metadata":{"assetId":"asset_123","buyerId":"user_456"}}}}'
T=$(date +%s)
SIG=$(printf '%s' "$T.$BODY" | openssl dgst -sha256 -hmac "$SECRET" | awk '{print $2}')

curl -X POST http://localhost:3000/api/webhooks/stripe \
  -H 'Content-Type: application/json' \
  -H "Stripe-Signature: t=$T,v1=$SIG" \
  -d "$BODY"

Doing it in a test

The same three lines, as a helper you can reuse:

import crypto from "node:crypto";

export function signedRequest(body: object, secret: string) {
  const raw = JSON.stringify(body);
  const t = Math.floor(Date.now() / 1000);
  const v1 = crypto.createHmac("sha256", secret)
                   .update(`${t}.${raw}`)
                   .digest("hex");
  return {
    raw,                                   // pass these EXACT bytes to your handler
    headers: { "stripe-signature": `t=${t},v1=${v1}` },
  };
}

Return the raw string, not the object. The whole point is that your handler verifies the bytes it received.

The events the CLI makes awkward

stripe trigger covers common happy paths well. It is the edge cases that tend to be where the bugs live, and those are easier to craft by hand:

CaseWhy it matters
Partial refund
amount_refunded < amount		 Should not revoke access — the buyer still paid for part of it. Easy to get backwards, and triggering a specific partial amount through the CLI is fiddly.
Redelivery
the same event twice		 Stripe delivers at least once. Sending the identical signed request twice is the cheapest possible test that fulfilment is idempotent.
Dispute
charge.dispute.created		 Should revoke regardless of amount. Rare in practice, so it is almost never tested.
Missing metadata Your handler should refuse rather than guess who bought what.
Hostile metadata
amount: "0.01"		 Proves the recorded amount comes from amount_total and not from anything a client can influence.
Stale timestamp Stripe enforces a five-minute replay window by default. A signature can be perfectly valid and still be rejected — worth seeing once so it doesn't confuse you later.

When you should still use the CLI

This isn't an argument against it. Use stripe listen when you want real events from your actual Stripe account flowing to your machine — verifying an end-to-end checkout, or watching what a real subscription lifecycle emits. Hand-signed requests are better when you want determinism: a specific payload, in CI, with no login and no tunnel.

One trap worth naming: the secret stripe listen prints is not the same as your deployed endpoint's signing secret. Using the CLI's secret against a deployed endpoint, or vice versa, produces a signature mismatch that looks exactly like a code bug.
